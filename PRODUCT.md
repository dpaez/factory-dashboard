# Product

<!-- impeccable:product-schema 1 -->

## Platform

web

## Users

Developers, software engineers, and AI engineers who personally run GEUT's factory (the Pi + factory-skills supervision system inside Docker sandbox compose kits). The dashboard is a personal operator companion: the same person drives tickets in the terminal (Herdr/Pi) and watches them in the browser alongside. Tone expectation: professional.

## Product Purpose

The operator's command center for one factory: where every ticket is, what needs a person, and what it costs, with the factory's commands sent on the operator's behalf. It turns the factory server API into a calm, at-a-glance overview so the operator knows where to pay attention without reading terminal panes. Success means the operator can see, in seconds, which tickets are active, which need their input, how far each ticket has advanced, and what it is costing.

## Positioning

A command center beside GEUT's factory (sbx-shell-pi image + factory-skills), backed only by the factory server API. Unlike generic agent-monitoring UIs, it speaks the factory's exact vocabulary (tickets, executions, tasks, runs, active agents, stages, statuses, review and QA rounds, attention requests, usage) and mirrors its real pipeline — no invented abstractions. The terminal remains a valid control path; the dashboard and the terminal send the same commands to the same factory server.

## Operating Context

- The operator runs factory tickets through the supervised flow: stages plan → work → QA → review → wrapup → done (QA is optional per factory), with the ten execution statuses queued / active / waiting_for_user / paused / resuming / resume_failed / failed / ready_for_handoff / complete / cancelled.
- The factory server owns the controller and serves a versioned HTTP API (`/v1`, OpenAPI at `GET /openapi.json`). It is the dashboard's only source of truth: the dashboard opens no state database, pins no schema version, and reads no views or `.factory/` files (ADR 0005, ADR 0002).
- The dashboard reads the API server-side on page load (SvelteKit + adapter-node). `FACTORY_API_URL` and an `act`-scoped `FACTORY_API_TOKEN` are private runtime env; an optional `FACTORY_OPERATOR_NAME` names the operator on commands. The browser never sees the token or the factory URL.
- A missing, unauthorized or insufficient-scope token renders a configuration error page, never an empty list. Data the API does not supply is shown as unavailable ("—").
- Usage setting: browser window alongside the terminal during factory runs.

## Capabilities and Constraints

- **Surfaces today (reads):** overview (open-ticket counts, needs-attention from the factory's `needsUser`, active agents, labelled open-ticket cost and tokens, stage cards including QA, open tickets table), tickets list (every ticket, cursor-paged, marked partial when the bound is hit), and ticket detail by ticket key with `?execution=n` (tasks with dependencies and review/QA summaries, attention requests with replies, the execution's usage total, executions, and runs with per-run usage).
- **Planned:** commands (start, reply, retry, stop, cancel, complete, rerun) and live updates from the factory event stream land in later tickets. Until then, interaction stays in the terminal.
- **Single factory:** one factory server per dashboard deployment. Multi-factory/multi-project is out of scope for now.
- The API carries verdicts, rounds, counts, usage totals and attention requests; detailed reviews remain in Pi sessions. It has no usage by stage and no cost on ticket summaries, so the dashboard shows those as unavailable rather than reconstructing them.
- Stack: SvelteKit (Svelte 5), TypeScript, Tailwind CSS 4, shadcn-svelte/bits-ui, TanStack Svelte Table, `openapi-fetch` with types generated by `openapi-typescript`, pnpm.
- Terminology follows `GLOSSARY.md`, which pins the factory-skills vocabulary: factory (the system, never a work item), ticket, ticket key, display reference, execution, task, run, active agent, stage, status, task status.

## Product Principles

1. **The factory decides.** The API's `needsUser`, stages, statuses and command validity are authoritative; the dashboard never derives attention or the next stage, and shows an accepted command as pending until a read confirms it.
2. **The API is the only source.** The dashboard renders what the factory server returns — verdicts, rounds, usage, attention requests — and invents nothing. Data the API does not supply is shown as unavailable, never reconstructed or shown as zero.
3. **Speak factory.** Exact vocabulary and pipeline shapes; no generic agent-monitoring metaphors.
4. **Answer "where do I look?" in seconds.** Open attention requests and waiting-for-user states are first-class; everything else supports them.
5. **Cost is a surface metric.** Token and USD usage belong on the main view, not buried in detail pages.

## Accessibility & Inclusion

No product-specific accessibility standard has been established. Light and dark modes are shipped and toggled manually; numeric data uses tabular figures.
